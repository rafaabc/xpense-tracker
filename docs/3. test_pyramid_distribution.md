## Distribution Overview

| Layer | Count | Percentage |
|---|---|---|
| Unit | 53 | ~40% |
| Integration — Mocked Dependencies | 28 | ~21% |
| Integration — Real Dependencies | 11 | ~8% |
| E2E | 12 | ~9% |
| Eliminated (duplicates/non-conditions) | 28 | ~21% |
| **Total (original conditions accounted for)** | **132** | **100%** |

**Assessment:** This distribution follows the pyramid shape — Unit is the largest layer, the two integration sub-layers together form a moderate middle, and E2E is kept lean and journey-focused. No ice-cream cone or UI-only coverage risk detected.

Splitting integration by coupling/mock-scope (rather than by "API test" label) surfaces that most integration-level conditions (28/39, ~72%) can run fast with the database/auth-provider mocked — only 11 genuinely need a real database or real session mechanism (constraints, cascades, joins, ordering, scheduled-job side effects, race conditions). This keeps the expensive real-dependency suite small and focused.

**Note on API Tests (16 conditions):** This layer is **cross-cutting**, not an additive 17th layer on top of the 132. It re-examines a subset of conditions already classified above (mostly from Real-Dependency Integration and a few from Unit/E2E) through the lens of HTTP contract — status code + response message — rather than data correctness or UI rendering. The same underlying test conditions, the same suite, can often assert both the contract (API layer) and the data correctness (Real-Dependency Integration layer) in one pass; they're listed separately here because they answer different questions ("did the endpoint respond correctly?" vs. "did the data end up correct?").

**Notes / Gaps:**
- TC-08-12-style "implied" conditions don't exist in the source list and were ignored.
- Cross-tenant protection conditions (TC-12-08/09, TC-13-08/09) were grouped at integration since they primarily test API-layer authorization against the DB; a lighter unit test on the authorization guard function could optionally be added.
- Recurring/renewal engine (US-08, US-09) is integration-heavy due to its reliance on scheduled job + DB state; consider contract-style tests if this logic is ever extracted to a separate service.

## ⚠️ Important Caveat: This Is a Starting Point, Not the Final Count

The numbers above (53 unit / 28 mocked-integration / 11 real-dependency / 16 API / 12 E2E) map the **132 test conditions from the backlog** — i.e. the *behavioral/acceptance* surface. They are **not** the full picture of how many tests will actually exist once implementation begins.

In practice, as each User Story is implemented:

- **Unit tests will multiply well beyond 53.** Each "pure calculation function," "validation function," or "service method" condition above typically expands into many individual test cases once you account for edge cases, boundary values, error paths, and branch coverage (e.g. TC-10-06 "Amount > 0" alone might become 5-10 unit tests: zero, negative, exactly 0.01, very large numbers, NaN, string input, etc.). It's realistic to expect the backend unit suite alone to grow into the **hundreds**, and the frontend component/unit suite (one or more tests per component, per prop combination, per interaction) to do the same.
- **Mocked-integration tests will similarly grow** as each service/repository/route pairing gets tested not just for its happy path but for each error/edge branch (repository throws, returns null, returns unexpected shape, etc.).
- **Real-dependency, API, and E2E counts should stay comparatively stable** — these are inherently expensive, so the pyramid principle argues *against* growing them proportionally; new conditions here should be rare and deliberate.

**Implication for coverage targets:** the 95% coverage threshold (backend unit/integration via c8, frontend unit via @vitest/coverage-v8) will be measured against this much larger, implementation-driven test count — not against the 132 acceptance-level conditions. This document should be treated as the **acceptance-level skeleton** (ensuring every backlog condition has a home in the pyramid), while the bulk of the coverage will come from additional, finer-grained unit/integration tests written alongside each implementation PR.

## Tool Suggestions (generic, by layer)

- **Unit:** Any fast in-process test runner (e.g. Jest/Vitest for JS/TS, JUnit/pytest for other ecosystems), with mocks/stubs for all external dependencies
- **Integration — Mocked Dependencies:** Same in-process test runner; mock the repository/auth-provider interfaces, assert on calls and returned shapes
- **Integration — Real Dependencies:** API-level test runner (e.g. Supertest/REST Assured) against an ephemeral/real test database and session store
- **E2E:** Browser automation tool (e.g. Playwright/Cypress), covering the critical journeys above against a deployed/preview environment

Concrete tool choices should follow once the architecture is modeled.
